# עוזר AI חכם — רכיב עצמאי לאישור

## מטרת הרכיב

הרכיב `ai_admin_assistant_standalone.py` הוא אב־טיפוס עצמאי לעוזר ניהול חכם בעברית. הוא אינו מחובר ל־`bot.py`, אינו משנה קובצי נתונים של הבוט ואינו מפעיל פעולות אמיתיות במערכת הפעילה.

המטרה היא לבדוק בנפרד את ההפרדה בין הבנת שפה לבין ביצוע פעולות: המודל מבין בקשה טבעית, מחזיר תכנית פעולות מובנית, ושכבת Python בודקת הרשאות ואישורי בטיחות לפני שהפעולה עוברת למתאם ביצוע.

## עקרון האבטחה

המודל אינו מקבל אפשרות להריץ Python, לערוך JSON, לגשת לקבצים או להחליט בעצמו אם למנהל יש הרשאה. הוא יכול לבחור רק פעולה מתוך רשימה סגורה. הקוד בודק את הפעולה, את ההרשאה, את יכולת העוזר ואת הצורך באישור מסוכן.

בגרסה הנוכחית מופעל `DryRunAdapter`, ולכן גם פעולה שאושרה נרשמת כסימולציה בלבד ואינה משנה את הבוט.

## מבנה הרכיב

### שכבת הבנת הכוונה

`HebrewAdminAssistant.plan()` שולחת את הטקסט למודל LLM ומבקשת JSON מובנה לפי סכימה קשיחה. הפלט יכול להיות:

- `actions` — רשימת פעולות לביצוע.
- `clarification` — שאלה למנהל כאשר חסר מידע.
- `unsupported` — הודעה כאשר הפעולה אינה קיימת במערכת.

הפלט נבדק לפני שימוש. פעולה שאינה ברשימת הפעולות המותרות נדחית.

### שכבת הרשאות

`ManagerContext` מייצג מנהל, את הרשאותיו ואת יכולות העוזר שלו. מנהל שאינו בעלים חייב להחזיק גם בהרשאת המערכת הרגילה וגם ביכולת העוזר המתאימה. בעלים עוקף את בדיקת ההרשאות, בהתאם למודל הקיים.

### שכבת אישור

פעולות מסוכנות אינן מתבצעות מיד. התכנית נשמרת ב־`pending_plans`, והעוזר מחזיר `confirmation_required`. לאחר אישור מפורש משתמשים ב־`confirm_pending()`. ניתן לבטל באמצעות `cancel_pending()`.

### שכבת ביצוע

`ActionAdapter` הוא ממשק שמיועד לחיבור עתידי לפונקציות האמיתיות של הבוט. כרגע `DryRunAdapter` רק מתעד את הקריאות. אין חיבור אוטומטי ל־JSON או ל־Telegram.

## פעולות מוגדרות

הפעולות המוגדרות כרגע הן:

- `set_daily_gift` — קביעת סכום מתנה יומית.
- `set_referral_reward` — קביעת תגמול הזמנה.
- `get_user` — בדיקת משתמש.
- `send_user_message` — שליחת הודעה למשתמש.
- `approve_purchase` — אישור רכישה.
- `add_coins` — הוספת מטבעות.
- `remove_coins` — הורדת מטבעות.
- `set_vip` — קביעת רמת VIP.
- `get_statistics` — קבלת סטטיסטיקה.
- `set_maintenance` — שינוי מצב תחזוקה.
- `find_duplicates` — הפעלת בדיקת כפילויות.
- `send_videos` — שליחת סרטונים למנהל.
- `delete_videos` — מחיקה מסוכנת של סרטונים.
- `restore_backup` — שחזור גיבוי.

רשימת הפעולות אינה הרשאה. לכל פעולה מוגדרת הרשאת מערכת נדרשת, וההרשאה נבדקת בזמן העיבוד.

## דוגמאות לכוונות שהרכיב מיועד להבין

- שינוי סכום המתנה היומית.
- שינוי תגמול ההפניה.
- שינוי שני הסכומים בהודעה אחת.
- בדיקת משתמש לפי ניסוחים שונים של מזהה.
- שליחת הודעה למשתמש.
- הוספה או הורדה של מטבעות.
- שינוי VIP.
- בדיקת סטטיסטיקה ומצב תחזוקה.
- בקשת פעולה שאינה קיימת, שאמורה להידחות במקום להומצא.
- פעולה מסוכנת, שאמורה להמתין לאישור.

## הפעלה ובדיקה

מתיקיית `telegram-bot` מריצים:

```bash
python3 -m py_compile ai_admin_assistant_standalone.py test_ai_admin_assistant_standalone.py
python3 test_ai_admin_assistant_standalone.py
```

הבדיקה אינה מתחברת לרשת ואינה נוגעת בנתוני הבוט. היא בודקת ביצוע של כמה פעולות בסימולציה, חסימת מנהל ללא הרשאה, דרישת אישור לפעולה מסוכנת ודחיית פעולה שאינה קיימת.

## חיבור עתידי לבוט

אין לבצע חיבור לבוט הפעיל רק באמצעות החלפת טקסטים. לפני חיבור עתידי יש:

- לחבר את שכבת הכוונה ל־ConversationHandler הקיים.
- לשמור על כפתור חזרה וביטול.
- לחבר כל פעולה ל־service או לפונקציה קיימת, ולא לכתוב JSON ישירות.
- להעביר את הרשאות המנהל והעוזר מה־`settings.json` הקיים.
- להוסיף שכבת אישור Telegram לפעולות מסוכנות.
- להוסיף הגבלת זמן לתכנית ממתינה.
- לא להכניס טוקנים, סיסמאות או מידע אישי ל־prompt או ליומן.
- להריץ את כל בדיקות הרגרסיה של הבוט לפני פריסה.
- לקבל אישור מפורש לפני כל עריכה של `bot.py` או חיבור לרשת.

## מצב נוכחי

הרכיב נבנה ונבדק בנפרד. `bot.py` לא נערך כחלק מהבנייה הזאת. אין שינוי בבוט הפעיל, אין שינוי במשתמשים, אין שינוי במטבעות ואין שינוי בגיבויים.
